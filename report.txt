 THE ONE PRINCIPLE
═══════════════════════════════════════════════════════════════════════════════

 Every element on screen is traceable to a physics model, a trained model, or a
 deterministic function — and the operator can see which.

 Enforced mechanically, not by discipline:

   npm run validate:data    parses every JSON against Zod schemas, asserts
                            invariants I1–I16. Wired into prebuild, so a drifted
                            number FAILS THE BUILD, not the demo.
   npm run check:literals   fails if a headline figure is hardcoded in src/.
   npm run test             145 tests, also wired into prebuild.

 Three invariants are tripwires against the author, not against bugs:
   I10  rejects a ΔT outside the measured band, so the thermal scaling cannot be
        quietly tuned to produce a nicer number.
   I11  rejects a detection confidence of exactly 0.84 — the spec's placeholder.
   I12  requires the agent to justify the drone dispatch.

 FINDINGS

 1. PROJECTED 72H LOSS IS 3.07 MWh, NOT 1.44  (C16)  ← changes a number on screen
    1.44 is 0.48 × 3, where 0.48 MWh/day was itself a seed value typed into
    plan/03 §7's queue table. The integral is fully determined — no free
    parameter — and the array's 105.4 kW shortfall across the forecast curve
    integrates to 3,069.7 kWh = 3.07 MWh (1.01 MWh/day).

 2. THE 14:00 DEADLINE NEEDED A DIFFERENT MODEL  (C18)
    A single threshold crossing cannot produce 14:00: the cell-temperature curve
    peaks near 12:30, so any threshold below the peak is crossed twice and the
    afternoon crossing is the module COOLING. Implemented as cumulative thermal
    dose: T_PROP_C = 65 °C, DOSE_BUDGET_H = 5.0 h.
    The budget is SOLVED to reproduce 14:00 and declared as such — same footing as
    f_mismatch = 0.4160 and P_RATED_STRING = 49.61.
    Note the asymmetry with finding 1: the deadline model HAS a free parameter, so
    a frozen observable can be honoured. The loss integral has none, so its frozen
    value had to move.

 3. INVERTER ROWS ARE A PEER STRING COMPARISON  (C17)
    A true inverter aggregate drives 40 arrays, so B-17's fault dilutes to ~−1%
    and §2's table would show nothing. Rows are the string at the inspected
    position on each inverter — what an operator actually looks at.

 4. FORECAST AMBIENT SPREAD IS 5.7 °C, AND THAT'S THE HONEST CONSEQUENCE  (C19)
    35 °C at 10:00 and a 38.1 °C peak over-determine the curve. Kept both frozen
    numbers and stated the result rather than fudging either. It actually helps:
    warm nights mean the module never sheds heat, which is why 72 clear hours is
    expensive.

 5. C9 RESOLVED — thermal_hotspot.py now imports BASELINE_TEMP_C from physics.py.
    Only the absolute baseline changed; the ΔT matrix, coordinates, cluster count
    and σ are byte-identical because nothing in the extraction reads it.

 HEALTH INDEX, since it's non-obvious
   94 → 80 is a severity roll-up: 100 − Σ deduction[status], warning 3.0,
   critical 14.0. An energy ratio would read 99.5% (120 monitored arrays are
   ~30 MW of a 500 MW block) and would hide the difference between "dirty" and
   "about to fail". Deductions scale with fault MAGNITUDE, not the status label,
   so health is continuous — max step 4.7/frame against I16's limit of 6.

 INTERLUDE — TWO BUGS YOUR EYES CAUGHT AND THE TESTS COULD NOT
═══════════════════════════════════════════════════════════════════════════════

 You said "the fonts and everything looks weird". Both were real.

 1. EVERY FONT WAS FALLING BACK TO THE BROWSER DEFAULT
    next/font variables were on <body>, but globals.css composes them into
    --font-mono / --font-cond / --font-sans on :root (= <html>). A custom property
    that references another resolves against the element it is DECLARED on, so
    var(--font-plex-mono) was undefined at :root, --font-mono became
    guaranteed-invalid, and the whole type scale silently died.
    No error, no warning. Moving the classes one element up fixed it.

 2. TABULAR NUMERALS WERE BEING DISCARDED
    The CSS `font:` shorthand RESETS font-variant-numeric — on exactly the .t-*
    classes that carry numbers. Farm health counting 94 → 80 would have jittered.
    Every mono class now restates it, with a comment so nobody tidies it away.

 jsdom caught neither: it has no font stack and doesn't resolve the cascade.

 ALSO: the debug readout was defaulting to visible. It is a build instrument, not
 part of the product. It now defaults on in development and OFF in a production
 build — nobody watching should see a scrub bar.

 ON THE KEYBOARD, since you asked whether this is a game:
   It is a presenter remote, not a game and not a product control surface. The
   90 seconds is a recorded incident being replayed; Space/arrows/speed/R exist so
   whoever is driving the pitch can start on cue, seek back when someone asks
   "what was that number", or slow to 0.5× while talking over the thermal scan.
   In real use the product has exactly ONE input: the operator clicks APPROVE.
   That is the entire interaction surface, and it is the point of the human gate.

 The check FAILS without it — the rationale must name soiling, name physical

 THE CROSS-CHECK
   Beyond structured fields, EVERY number in the free-text reasoning is checked
   against a set built from the data itself. That is where a fabricated figure
   actually hides: the reference implementation's own agent output says "matching
   the client-reported 60% output drop" while its telemetry says 58.4%, and
   nothing caught it. This would have.
   A stage that fails is retried with the rejection as a correction; after four
   attempts the script exits non-zero and writes NOTHING.

 IT CAUGHT FOUR THINGS — THREE WERE MY ERRORS, NOT THE MODEL'S
   1. It flagged "17" out of "B-17". Identifiers contain digits that aren't
      measurements. A check that cries wolf is a check that gets switched off.
   2. I demanded suspectComponent == "INV-B". The model answered "String
      B-17-S3", which is MORE precise — the fault is inside the string, INV-B is
      only where it is observed. I was forcing a worse answer.
   3. prognosis.confidence came back as 5, which Zod rejects.
   4. THE GENUINE CATCH: my prompt exposed THERMAL_SPAN_C as a bare "25 C span",
      and the model wrote that the cells run "2.8 °C above the nominal 25 °C
      span" — two REAL numbers in a physically WRONG sentence. Numeric checks
      can't see that. Removed the loose number; it now correctly says
      "2.7–2.8 °C above the array median".

   Also tightened severity: the model first said "medium", which would have sat
   beside a console badge reading CRITICAL. A >50% string shortfall with a
   same-day deadline isn't medium — diagnostic ambiguity belongs in confidence.

 typographic() swaps the ASCII hyphen the model writes for U+2212 so agent prose
 matches the tables beside it. GLYPH ONLY — no word, digit or unit altered, and it
 will not touch B-17 or INV-B. That last case has its own test, because silently
 corrupting every component ID would be a nasty way to fail.

 THE IRONBOW CONSISTENCY CHECK - the item plan/05 names for this phase
   The seven stops existed in THREE hand-typed copies: globals.css tokens, a
   nearest-stop lookup in AnomalyMatrix, and vec3 literals in the GLSL shader.
   Nothing compared them. A drift of one stop would have broken the project's one
   aesthetic bet SILENTLY - nothing would look broken, it would just stop meaning
   anything.
   Now src/lib/ironbow.ts is the only definition. The matrix calls it; the shader
   is GENERATED from it; and ironbow.test.ts READS globals.css OFF DISK and fails
   if a token has drifted. 18 tests, including that the GLSL and the TypeScript
   interpolate identically across the whole domain to within one rounding step.
   Fixed while there: the matrix used arbitrary delta-T thresholds. The domain is
   now the measured range (-6.5 .. +3.2 C), so the hot band lands in the amber end
   where a thermographer expects heat.

 A REAL ACCESSIBILITY BUG
   Every control used `all: unset` as an INLINE style. Inline styles outrank the
   stylesheet, so that also unset the focus outline - and no :focus-visible rule
   could restore it. Keyboard users had no visible focus anywhere in the app.
   Replaced with a .btn-reset class carrying its own focus ring. All three
   controls are real <button> elements and are reachable on Tab.

 prefers-reduced-motion
   The CSS media query cannot reach framer-motion's JS-driven animation, and the
   feed's slide-in is JS-driven. Wrapped in <MotionConfig reducedMotion="user">.
   The MATRIX FILL deliberately still runs - it is information, not decoration.

 SCENE PALETTE
   plan/04 bans raw hex in src/components/. All remaining hex was in the 3D scene,
   where three.js materials cannot read CSS variables - and the panel blue was
   written out twice. Pulled into src/lib/scenePalette.ts, every value cited to
   CLAUDE.md section 14.

 MOTION AUDIT - clean. No springs, no bounces, no easing on anything that carries
   meaning. Every transition is linear, 120-200 ms. The two CSS animations (REC
   pulse, reticle breathe) are presentational and no selector reads them.

 TEST HARNESS
   The PiP assertion was timing out at 5 s as the console got heavier. Replaced
   with a STRONGER and cheaper one: the console's entire rendered text must appear
   inside the cinematic's as one contiguous run, since the PiP renders ConsoleRoot
   whole. A screenshot, a mock or a simplified copy all fail it.

   could not catch and which was burying real output.

 1. CONTROLS THAT WERE PROPS

    Six controls were lifted off the reference screenshot and never wired. They
    sat where controls sit, they looked like controls, and every one did nothing.

      QUEUED              was a bordered box among two buttons. It is a STATUS,

      INSPECT EVIDENCE    a real button. Scrolls the rail to the inspection group.
      OVERRIDE            a real control, and the other half of the approval gate.

                          records the operator's decision WITH a reason, shows it
                          on screen, and can be cleared. It raises no work order -
                          declining is not approving.
      FILTER              cycles the event feed's severity floor: all / warning+ /
                          critical. It filters the FEED and deliberately not the
                          mission log, because hiding rows from a list is a choice
                          about a list; making the drone stop reporting what it
                          found is a different thing.
      VIEW ALL EVENTS     expands the feed past its six-row preview, and says how
                          many rows that is.
      VIEW QUEUE ->       navigates to the Repairs screen. It has sat next to a
                          working repairs module since Phase 13.

 2. ONE FAULT WAS NEVER ENOUGH TO USE THE CONSOLE WITH

    data/scenario.json carried a single event. An operator could look at exactly
    one interesting array and 119 identical healthy ones, so nothing could be
    compared against anything and most of the console could not be exercised at
    all.

    THREE CRACKS, THREE DEPTHS. The same mechanism - a cracked cell driving its
    bypass diode into conduction - separated by how many of the array's seven
    strings the crack has reached and how far the mismatch derate falls:

      A-31  11:20   2 of 7 at 0.68     string -32.0%   array  -9.1%   warning
      B-17  10:04   5 of 7 at 0.4160   string -58.4%   array -41.7%   critical
      C-07  12:40   6 of 7 at 0.34     string -66.0%   array -56.6%   critical

    B-17's pair is untouched. It is the array the committed evidence, the cached
    agent run and every invariant describe, and it does not move.

    evaluateArray gained faultedStrings and terminalMismatch as PARAMETERS,
    defaulted to B-17's frozen pair - so the golden test that recomputes the whole
    committed telemetry.json from the TypeScript is byte-identical, and a crack is
    no longer one size.

 3. INJECTION, AND WHY IT IS NOT A BACK DOOR

    A sixth module screen - SCENARIO - injects a fault onto any array on demand:
    four mechanisms (hairline / established / advanced crack, string outage), a
    ramp, a live preview of the deviation the physics WILL produce.

    It writes a SCENARIO EVENT and nothing else. There is deliberately no way to
    type a deviation onto an array. Everything that then appears - output,
    deviation, status, cell temperature, queue position, the event feed line - is
    computed by the same model that evaluates the committed faults. That is the
    difference between a test case and a fabrication, and the whole project rests
    on it. injection.test.ts asserts the injected object's key set exactly, so a
    future field that smuggles in a reading fails the build.

    Injected faults are marked wherever they surface: in the feed, in the verdict
    block, in the queue. A rehearsal presented as site history would be the same
    class of lie as B-17's evidence shown under another array's name.

 4. THE RIGHT RAIL NOW MAKES AN ARGUMENT

    Reported: "too much info, seems unorganised, not telling a story". Correct.
    It was twelve peer sections in the order they were BUILT, and on a healthy
    array the first thing it said about C-29 was a three-line paragraph about
    something it did not have.

    Five groups, in the order an operator reasons:

      STATE       what the array is doing, measured
      ASSESSMENT  what the agent makes of it, and when it said so
      INSPECTION  what a drone was sent to find out, and what came back
      OUTLOOK     what the weather does to it over 72 hours
      DECISION    what the operator is being asked to authorise

    Each group is one claim; blocks inside it are the evidence. A block with
    nothing to say is absent rather than apologetic - "no capture on file" went
    from being a section header to one sentence at the point where the imagery
    would have been.

 5. FOUR UNTRUTHS IN ONE SCREENSHOT

    The reported C-29 panel had, in one view:

      "Inspected - evidence captured"  directly above  "no capture on file"
          Two flatly contradictory statements four lines apart. The mission proves
          the drone went and looked; whether committed imagery came back is a
          separate fact and is now stated separately.

      Output 0.00 kW / Expected 0.00 kW / Irradiance 0 W/m2 at 35.6 C ambient
          That is night. The deviation formula divides zero by zero, floors to
          0.0%, and statusFor calls it HEALTHY - so a cracked array would read
          clean all night. The console now says NO GENERATION - AFTER SUNSET and
          withholds the deviation rather than printing arithmetic on two zeroes.

      Fleet health climbing back toward 100 after dark
          Terminal status was evaluated at the CURRENT hour. It is now evaluated
          at reference conditions: a fault is a property of the array, not of the
          time of day.

      "Projected loss 3.07 MWh / 72 h" under a healthy array
          B-17's committed integral printed under every array in the site. Now
          scaled by the selected array's own shortfall at reference conditions -
          B-17 still reads exactly 3.07, and C-29 reads "none - C-29 is not

    Related, found while fixing it: the live event feed sourced EVERY fault on the

 6. THE LIVE QUEUE STOPPED DROPPING WORK, AND STOPPED EMPTYING AT NIGHT

    A crack's deadline is COMPUTED - the hour its cumulative time above the
    propagation threshold reaches the declared dose budget - which is the entire
    claim the prognosis stage makes. The queue nevertheless LOOKED IT UP, and only
    B-17 had a committed record, so a second cracked array fell out of the queue
    and was reported as "unrankable". Nothing about it was unrankable; the
    deadline was never asked for. crackDeadlineHour() now computes it, in

    The queue also read its shortfall off the live frame, so at sunset it emptied
    completely and refilled at dawn. It now quotes shortfall at REFERENCE
    conditions: a cracked array costs the same at midnight; the sun is simply not
    up to prove it.

    CLAUDE.md sec 3 and sec 9.4 both describe it. There were zero references to it

                      every number in the prose goes through the same cross-check

 PHASE 17 - HEAT ON CELLS, MARKERS ON THE GROUND, AND A BROWSER AT LAST
================================================================================

 Two visual changes to the 3D cinematic, and the first tool on this machine that
 opens the product. The tool found more than the changes did.

 1. THE THERMAL VIEW HEATS CELLS, NOT MODULES

    CrackedPanel set mat.emissiveIntensity, which is a whole-material property,
    so a broken module glowed as one solid rectangle. A real IR frame of a
    bypassed substring shows a hot BAND with the busbars dark between the cells,
    because the cells dissipate and the interconnects do not.

    The heat is now an emissive MAP drawn on the same 5x7 lattice the surface
    texture already used. The scalar says how far into the thermal pass we are;
    the map says where the heat is. The lattice is stroked black on the emissive
    canvas and each lit cell is inset by the busbar width, so the dark grid
    survives between two adjacent hot cells.

 2. WHICH CELLS LIGHT UP - A THREE-WAY SPLIT, NOT A TWO-WAY ONE

    CrackedPanel's docstring described two kinds of claim. There are now three,
    and the docstring says so:

      the crack polyline              a MECHANISM the site record declares
                                      hasCrackMechanism() - many arrays
      heat on the cells it crosses    the same MECHANISM, illustrated
                                      hasCrackMechanism() - many arrays
      heat on the measured row-2 band a MEASUREMENT from a real UAV capture
                                      hasCapturedEvidence() - B-17 AND NOBODY ELSE

    The line to hold is between the second and third. A non-B-17 array may show
    hot cells, but they are derived from the illustrated crack path and never
    from cellGrid.defects. Reading cellGrid.defects for another array would be
    the seventh instance of this project's most repeated bug.

    So the choice does not live in the component. src/lib/panelCells.ts is pure
    and holds the crack polyline once - the stroke and the crossed-cell set are
    both derived from it, where they used to be two lists that could drift - plus
    hotCells(), which is the gate. panelCells.test.ts asserts each branch is
    structurally what it claims: the measured branch is exactly the committed
    defect set weighted by its own dT, and the illustrated branch is exactly the
    polyline derivation at one flat weight. A gradient across illustrated cells
    would be a temperature reading nobody took.

    The accepted risk, recorded so it is not rediscovered as a bug: a non-B-17
    thermal view now looks more evidential than it strictly is. Two things keep
    it honest and must not be undone - the console's AnomalyMatrix stays
    B-17-only, and the cinematic's detection label stays gated on cue.cracked.

 3. THE ARRAY ID TAGS ARE PAINTED ON THE DIRT

    They were projected from the array centre at POST_HEIGHT + 0.9, a metre above
    the modules, so each one hung in mid-air beside the panels it named. They now
    project from labelAnchor() - a point on the ground, PANEL_H/2 + 0.3 m toward
    the low edge of the tilt, which clears the module's own ground footprint of
    0.73 m with a third of a metre of sand to spare. During the crossing the tags
    sit in the service corridors between rows, which is where a site paints them.

    The offset cannot simply be made larger: the camera orbits the module at
    15 deg/s from 5.6 m up, so a world-fixed offset swings across the frame, and
    at 2.5 m the tag leaves the shot during the pass.

 4. projectToScreen WAS MIRRORED - FOUND BY LOOKING, FIXED HERE

    It built `right` as (fz, 0, -fx), which is the camera's LEFT. Both basis
    vectors came out flipped, so every projected point landed rotated 180 degrees
    about the centre of frame.

    Nothing caught it in 345 tests. reticleRect bounding-boxes four corners
    symmetric about the target, and the camera looks AT the target, so that box
    is centred on the middle of frame - a point reflection through the centre
    returns it very nearly unchanged. The reticle was accidentally right. The
    panel ID tags were the visible casualty: each was drawn on the far side of
    the frame from the array it names, which is precisely the doubt those tags
    exist to answer. It only became obvious once they were anchored somewhere
    asymmetric enough to notice.

    scene.test.ts now checks the projection against a real three.js
    PerspectiveCamera across three arrays and the whole flight, rather than
    against itself. A hand-rolled projection needs an independent oracle.

 5. A BROWSER ON THIS MACHINE

    Every visual bug of the last two sessions reached the owner's screenshot
    instead of being caught here. scripts/shoot.mjs drives the real console in
    the Chrome that is already installed, through playwright-core - a 3 MB dev
    dependency, no browser download, no second engine to keep current.

      npm run shoot -- B-17 14 52     array, site hour, point on the scene clock

    It clicks the controls an operator clicks rather than reaching into the
    stores, so what it proves is what an operator would see. Two things it had to
    learn, both recorded in the file:

      The day scrub steps in 15-minute jumps and a range input snaps to its own
      step lattice however you write to it, so it can only express scene seconds
      18, 33, 48, 63 - which misses the entire thermal window bar its first frame.
      It jumps to the lattice point below the mark and lets the site clock run the
      rest, POLLING the on-screen timecode rather than waiting a wall-clock
      interval: the one rAF loop clamps dt to 0.1 s per frame, so under SwiftShader
      the clock advances at the frame rate and not at real time.

      After the cut to the cinematic the console survives only inside the PiP,
      which is aria-hidden and drawn at 0.31 scale behind overlays. Roles cannot
      see it and a real click would be intercepted, so controls are pressed by
      aria-label through a dispatched event.

    Output goes to docs/shots/, which is gitignored. The script is reproducible;
    the PNGs describe one moment on one machine.

 6. THE DEV SERVER TRUNCATES ITS OWN BUNDLE - OPEN, docs/backlog.md 6b

    data/telemetry.json ships in the client bundle, all 1.1 MB of it, as a single
    JSON.parse('...') line in chunks/app/layout.js. The dev server truncates that
    chunk on roughly one load in two. The browser throws SyntaxError, hydration
    never runs, and THE PAGE STILL LOOKS COMPLETELY CORRECT because the

 PHASE 18 - THE DEMO SURVIVES THE ROOM, AND THE CONSOLE STOPS TALKING TO ITSELF
================================================================================

 Steering pass ahead of CodeYourCult (5-6 Sep). The product was reviewed against
 what a judge actually evaluates rather than against the build plan, and the
 finding was that the biggest risks were not missing features. They were: a page
 that could render perfectly and ignore every click, a screen full of vocabulary
 nobody outside the trade reads, and two surfaces contradicting each other in
 front of the operator. docs/hackathon-checklist.md is the running list.

 1. 1.6 MB OF TELEMETRY WAS REACHING THE BROWSER

    Known since Phase 17 and recorded as open. The dev server truncated the chunk
    carrying it on roughly one load in two; the browser threw a SyntaxError,
    hydration never ran, and THE PAGE STILL LOOKED COMPLETELY CORRECT because the
    server-rendered markup was all there. Nothing responded to a click.

    The demo is one incident on one array, so across all 91 frames exactly ONE of
    the 120 arrays ever changes. The other 119 were stored identically, ninety-one
    times over. data/telemetry_client.json stores the base once plus the per-frame
    differences: 1617 kB -> 52 kB, 3.2%. layout.js in dev went from carrying the
    whole file to 405 kB total.

    It is a SHIPPING FORMAT, not a summary, and that distinction is the whole
    safety of it. pack_telemetry.ts packs, unpacks with the function the
    application itself uses, re-serialises, and refuses to write unless the bytes
    match the original exactly. telemetryPack.test.ts asserts the same against the
    committed pair, reading both off disk so it compares two artefacts rather than
    a value against itself. telemetry.json remains the source of truth and every
    invariant is still asserted against it.

 2. THE DEMO MUST RUN FROM A PRODUCTION BUILD

    Measured rather than assumed. scripts/check_live.mjs loads the real console in
    the real browser, waits for the liveness chip to flip, and then presses a key
    an operator presses - so what it proves is that the app RESPONDS, not merely
    that it painted.

      next dev     dead on 1 load in 10. The scene chunk is 12 MB unminified and
                   page.js 9.6 MB; a chunk that size truncates whatever else is
                   fixed.
      next start   awake on 20 of 20.

    A dead network threw and was handled. A network that ACCEPTED the connection
    and then stalled did neither: the console pulsed "Triaging B-17..." forever. A

================================================================================
 PHASE 19 - THE INCIDENT, THE COST OF WAITING, AND TRIAGE THAT MEANS TRIAGE
================================================================================

 Groups C through H of docs/hackathon-checklist.md. The steering review found the
 product was a very good description of the present and had almost nothing to say
 about a decision. These are the four things that changed that, and the six bugs
 found on the way - every one of them by looking at the running console.

 1. THE INCIDENT IS ONE OBJECT - src/lib/incident.ts

    Everything the product knew about a failing array was already on screen and
    spread across a dozen components that had never been introduced to each other.
    Each was correct; together they were a list of facts rather than an argument.

    An incident IS the argument, and it has a shape: observed, checked, diagnosed,
    projected, recommended, decided. DERIVED, never stored - a pure function of
    the site at a moment plus what the operator has done, so scrubbing time
    backwards rewinds it and there is nowhere for a stale one to hide.

    ONE STRUCTURE, TWO VIEWS. The timeline is the chain filtered to steps that
    happened, sorted by when. They cannot disagree, because there is only one.

    Every step carries the BASIS of its claim - measured / from the model /
    calculated / declared assumption / written by the agent / operator - and the
    name of what produced it. Deliberately NOT colour-ranked by trustworthiness: a
    declared assumption is not worse than a measurement, it is different, and the
    reader gets to decide what that is worth.

    The dossier became the INCIDENT FILE. It had been gated on captured imagery,
    which would have hidden the product's central argument behind the one array
    that has a photograph. The gate MOVED to the imagery column - the only part
    that was ever scoped - rather than lifting.

 2. WHAT WAITING COSTS - src/lib/defer.ts

    The one thing here a detector cannot do. Fix now, in six hours, tomorrow, or
    in three days, with the energy never generated for each.

    THE STEP IS THE POINT. Up to the deadline the array is derated. Past it the
    declared mechanism is that the bypass diode fails, which OPENS the strings
    rather than derating them - modelled exactly as string-outage is modelled
    everywhere else, terminalMismatch 0 through the same evaluateArray. That
    discontinuity is what makes a deadline a deadline rather than a suggestion.

    A window is a FRACTION of the committed integral, never a second integral.
    Recomputing gives 3.058 where the committed figure is 3.07, and two answers
    for B-17's loss on one screen would cost more than the third decimal is worth.
    A test asserts the full window reproduces the committed figure exactly.

    Measured on screen at 17:30 site time: Now 0.00 / In 6 h 0.01 / Tomorrow 1.75
    / In 3 days 4.02 MWh. The six-hour figure is near zero because those six hours
    are night, which is the model being right rather than a bug.

    No cliff is ever claimed for an array without a computed crack deadline. Dirt
    gets worse linearly and nothing catastrophic is asserted about it.

 3. TRIAGE THAT SORTS DIFFERENT PROBLEMS - src/lib/causes.ts

    Until this existed the site had one mechanism at three depths, so every
    incident ended in "fly the drone, replace the module". A system that always
    reaches the same conclusion is a detector with extra steps.

    THE FIRST VERSION WAS CIRCULAR AND WAS REWRITTEN. It diagnosed soiling by
    reading the array's f_soil out of the committed scenario - which is the
    ANSWER, not the evidence, and no operator on a real site can see it. A triage
    engine that consults ground truth is looking up, not triaging.

    It now discriminates on the SHAPE of the loss, from readings an instrument
    actually produces:

      SOILING   the whole array down evenly, cell temperature at the fleet
                median. Dirt reduces the light going in, so it reduces heat as
                well as power.
      A CRACK   one string far below the others, and that string running hot,
                because a reverse-biased substring dissipates what it no longer
                exports.

    A test greps the module to assert it never reaches for soilFor or eventFor.

    SHADING IS WHY THE 3D EARNS ITS PLACE. Whether a row can shade the one behind
    it is decided by tilt, row pitch and solar elevation, and none of those is
    visible on a flat map - a 2D plan has no height and no tilt, so it cannot
    answer the question at all. At this site (25 deg, 8 m pitch, 1.6 m collector)
    the limit is 5.9 deg, so shading is a dawn-and-dusk phenomenon and is RULED
    OUT at midday BY GEOMETRY. That elimination narrows the diagnosis without
    adding a loss term to the frozen physics. The 3D is not a picture of the
    answer; it is where part of the answer comes from.

    THE REFUSAL MATTERS MORE THAN THE DISPATCH. Measured on screen for A-08, from
    the live model: "All seven strings show a similar ~11.34% power shortfall
    while cell temperature matches the fleet median... imaging is not required to
    confirm soiling; cleaning the array is the appropriate action." Confidence
    0.92, physical verification NOT REQUIRED.

 4. THE QUEUE BECAME A DAY - src/lib/schedule.ts, src/lib/money.ts

    Ranking without scarcity is sorting. rankQueue produced a perfectly good
    ordered list and nothing acted on it.

    A greedy pass down the existing ranking, each job taking whichever resource
    frees up first. DELIBERATELY NOT AN OPTIMISER: a solver gives a better
    schedule and an unarguable one, and the entire value of priorityScore is that
    a person can read it and disagree. accessCost, which has been in the committed
    queue since the beginning and until now only ever divided a score, moves a
    clock here.

    On screen: "With 2 crews and 2 aircraft, 2 of 4 jobs finish after their
    deadline - B-17, A-31. They are not late because they are unimportant; they
    are late because higher-ranked work has both crews." The "what would another
    crew buy" answer re-runs the identical model rather than estimating.

    MONEY IS AN ASSUMPTION THE OPERATOR OWNS. CLAUDE.md sec 1 forbids quoting a
    tariff we cannot source, and that rule stands. It does not mean money cannot
    appear - it means money cannot appear as a FACT. The tariff is shown next to
    every figure derived from it, changeable with a slider, persisted, and
    captioned "an assumption you set, not a sourced tariff". Rupees group the
    Indian way, because the site is in Rajasthan.

 5. SIX BUGS, ALL FOUND BY LOOKING

    THE AGENT'S VERDICT NEVER EXPIRED. Triage was cached per array and never
    re-asked. Select B-17 at 10:00, its crack begins at 10:04, and the console
    then carried "all metrics are within tolerance, physical inspection is
    unnecessary - confidence 1.00" under a CRITICAL badge and a -41.7% deviation,
    permanently. The cache is now keyed on the array's CONDITION as well as its
    id: a change in what there is to judge invalidates the judgement.

    THE CROSS-CHECK FORBADE THE RIGHT ANSWER. agentCheck demanded
    requiresPhysicalVerification true for ANY materially deviating array - the
    rule you write when the site has one fault type. It made "book the wash crew
    instead of flying" an answer the model was not allowed to give. It now
    enforces the same signature rule the deterministic diagnosis uses, importing
    the thresholds rather than restating them.

    THE PROMPT INSTRUCTED THE MODEL TO CLAIM AMBIGUITY IT COULD RESOLVE. It said
    soiling and cell damage always look alike and only imaging can separate them.
    Rewritten around the two signatures, with an explicit line: do not claim
    ambiguity you have the evidence to resolve, it wastes a sortie.

    THE CRACK'S ESCALATION WAS BEING APPLIED TO DIRT. The forecast step told a
    soiled array that "the cell crosses its heat threshold in 25.9 hours", and the
    cost-of-waiting would have warned that its bypass diode was about to fail. A
    soiled array has no cell to crack and no diode to fail.

    MODULE BODIES PAINTED BLOCKS OVER EACH OTHER, ON ALL FIVE SCREENS. The body
    was a grid whose auto rows stopped agreeing with their children: a slab
    holding 400 px sat in a 135 px row, overflowed it visibly, and drew straight
    over the block beneath. Two blocks with very different content came out
    identical heights, which was the tell. It predates this session. The body is a
    flex column now - no row-sizing step to get wrong - and all five screens are
    verified by measuring content height against rendered height in a browser.

    A SECOND PROVENANCE LINE THAT CONTRADICTED ITS OWN CLAIM. "the ambiguity is a
    property of the telemetry" printed under a step that had just said there was
    no ambiguity and no inspection was needed.

 6. TWO WORKFLOW TRAPS THAT MAKE A DEMO LOOK BROKEN

    Rebuilding underneath a running `next start` cost real time twice. The old
    server keeps serving HTML referencing chunk hashes the rebuild deleted, so the
    browser 404s on every script and hydration never runs; `next start` then fails
    with EADDRINUSE and leaves the STALE server alive, so the failure is silent
    unless you read the log. `npm run demo` is now scripts/serve.mjs: kill the
    port, wipe .next, build, serve, in that order.

    A .next holding both dev and production artefacts breaks _document and
    produces 404s that look like a code fault.

================================================================================
 PHASE 20 - THE OWNER OPENED IT ON A LAPTOP
================================================================================

 Everything in Phase 18 and 19 was checked against a 1920x1080 screenshot. Phase
 20 is what happened when the product was opened on a real 1512x900 laptop screen
 by somebody who did not write it. Four contradictions, one standing complaint,
 and two features.

 The complaint, verbatim: "all other pages are also just a cluttersome place,
 nothing looks good, i dont even know where to start, we need to really reduce the
 amount of text and jargon spam everywhere every single page."

 That is docs/ui-brief.md's complaint from August, again. The redesign answered
 HIERARCHY and left DENSITY alone.

 1. FOUR THINGS THAT CONTRADICTED THEMSELVES

    A SCHEDULED ARRAY SAID "WITHIN TOLERANCE. NO INTERVENTION SCHEDULED."
    `status === 'scheduled'` had no branch in StatusChips and fell through to the
    healthy sentence. It printed under a SCHEDULED badge, beside a -41.7 %
    deviation and a named crack mechanism: three claims, two of them false, in one
    box four lines tall.

    B-17'S FINDINGS PRINTED UNDER A-08. `Findings` renders the committed cache,
    which is B-17's and only B-17's; the dossier gated it on `agent` alone. So
    A-08's incident file carried "INV-B output is -58.4%... string B-17-S3... 5 of
    7 strings faulted". The TENTH instance of this project's most repeated bug,
    and it was introduced in Phase 19 by adding a section without asking whose
    data it was. Every new surface has to answer that question.

    THE AGENT ARGUED WITH THE CONSOLE ABOUT TEMPERATURE, AND THE AGENT WAS RIGHT.
    The chain said "that string is running 2.8 C hot". The model, given the same
    facts, replied that it lacked per-string temperatures and therefore could not
    say - and dropped to confidence 0.70 on a case it should be certain about.
    It was correct: the thermal reading is an ARRAY average against a fleet
    median. The prompt had been written telling it to look for a hot STRING, which
    is a measurement nobody takes. The prompt, agentCheck and causes.ts now all
    describe the array-level rise that is actually measured, and the prompt says
    explicitly not to treat the absence of per-string data as a blocker.

    A PROVENANCE LINE THAT CONTRADICTED ITS OWN STEP: "the ambiguity is a property
    of the telemetry" printed under a step that had just said there was no
    ambiguity and no inspection was needed.

 2. IT DID NOT FIT THE SCREEN

    CLAUDE.md sec 3: "Desktop only, fixed 1920x1080. Do not spend time on
    responsive layouts - this runs on a projector." Right for a recording, wrong
    for a product somebody opens on a laptop: the console sat in a box with black
    space around it and the right-hand third was off the edge.

    SCALED, NOT REFLOWED. The design stays 1920x1080 and the browser draws it at
    whatever size the window allows, like a slide fitting a projector. Reflowing
    would have meant rebuilding six screens and re-pinning every test that asserts
    what is on screen at a given second; scaling keeps the hierarchy the redesign
    fought for - at 79 % on a 1512x900 laptop the 52 px figures are still 41 px.

    Centred by ABSOLUTE POSITION, not by grid alignment. `place-items: center`
    leaves an item WIDER than its container at x=0; the transform then scaled it
    about its own middle and the console started 204 px in and ran off the right
    edge, which is very nearly the bug this was meant to fix.

 3. SHOW WORKINGS - OFF BY DEFAULT

    Every grey provenance line on this console exists to answer one question: how
    do you know that? It is the most important thing here when a judge asks and
    pure noise the rest of the time, and it was on screen permanently, in nine
    places per screen. "expected output from physics.ts". "as at 12:03 ·
    openai/gpt-oss-120b". "Every number above was checked against this array's
    telemetry before it was shown."

    One switch in the header, off by default. The claim stays visible; the receipt
    is one click away, which is the second it is actually wanted. Implemented as a
    class on the root and a `workings` class on the lines, so every component stays
    a pure function of the store and the demo-script tests keep working in either
    state.

 4. TWO THINGS THE SHELL CAN NOW DROP

    THE EVENT RAIL was on every screen on the grounds that events do not stop
    happening because you changed screens - true, and beside the point: on
    Repairs, Analytics, Drones and Missions it was a fifth of the width spent on
    something you are not looking at.

    THE DETAIL RAIL held a third of the console permanently, including when
    nothing was selected and it read "NO ARRAY SELECTED". It is a panel over the
    map now: the map gets the full width, and the rail arrives when an operator
    asks a question of an array. It needed `display: none !important` - DetailPanel
    sets `display: grid` inline, and an inline style beats a class however specific
    the selector.

    THE DOSSIER was a full-width band of reasoning with two columns beneath it,
    which on a laptop pushed the captured frames below the fold: the operator had
    to scroll to reach the photograph the drone was sent for. Reasoning down the
    left, material down the right, both visible at once.

 5. LIGHT MODE

    Forbidden outright by CLAUDE.md sec 3. The owner asked for it after using the
    product in daylight, which is a case the spec did not consider. That is the
    decision; the line is superseded rather than quietly ignored, and the CSS says
    so.

    THE IRONBOW RAMP DOES NOT INVERT. It is the actual false-colour LUT a thermal
    camera uses, and the whole reason it is this console's semantic palette is that
    the interface's colours and the camera's colours are then the same colours. A
    "light ironbow" would be a different instrument. Surfaces, lines and text
    invert; the ramp is only ever read against a surface, never as one.

    The `-ink` variants had to go the other way: darker rather than lighter, or a
    42 px critical figure washes out on a near-white ground.

 6. THE DETECTOR RUNS IN THE BROWSER NOW

    Asked directly: "why is the detection an animation instead of running yolo
    model?" The honest answer was that the box IS real model output - YOLOv8n at
    0.9084 on a held-out image - computed once and replayed, and replayed looks
    exactly like animation. The most rigorous thing in the project read as the
    least.

    The fix is not to install torch here, which CLAUDE.md forbids and which would
    not help Vercel anyway. It is ONNX: the same weights, exported once, running on
    WebAssembly in the operator's browser on a frame captured from the 3D scene a
    second earlier. "That box isn't saved. Watch."

    WHAT IS IN src/lib/detect.ts is the arithmetic either side of the model, which
    is the part that is actually work. THE SHAPE IS THE TRAP: v8 emits
    [1, 4+classes, anchors] - the transpose of v5, and with no objectness column,
    the class score IS the confidence. Reading it the other way round produces
    boxes that are plausible, wrong, and completely silent about it. Sixteen unit
    tests against hand-worked cases.

    THE FRAME IS THE DRONE'S OWN CAMERA. `preserveDrawingBuffer` on the R3F canvas,
    read back with toDataURL. Without that flag WebGL is free to clear the buffer
    after compositing and the capture comes back blank - silently.

    NO BOX IS EVER DRAWN FROM ANYTHING BUT MODEL OUTPUT. The scene knows exactly
    where the crack is - panelCells.ts holds the polyline - and using it to place a
    rectangle labelled as a detection would be fabricated evidence. A test asserts
    an empty tensor yields an empty result.

    Four honest states: no model (the export has not been run), running, found, and
    FOUND NOTHING - which is a real answer, because the detector was trained on
    ground-level photographs and a rendered panel is not one. If it finds nothing
    the panel says so and the committed photograph keeps its detection.

    OUTSTANDING: the export itself, docs/colab-export-onnx.md, which needs a Colab
    account and two minutes. Until it is run the console says the detector is not
    loaded and draws nothing.

 7. A LAYOUT BUG FOUND BY MEASURING RATHER THAN LOOKING

    Module bodies were a grid whose auto rows stopped agreeing with their children:
    a slab holding 400 px sat in a 135 px row, overflowed it visibly, and painted
    over the block beneath. Two blocks with very different content came out
    identical heights, which was the tell. Present on all five module screens and
    predating this session. Now a flex column - no row-sizing step to get wrong -
    and scripts/shots.mjs photographs every screen in both themes so the next one
    is caught by looking.

 Two jobs. Investigate a button reported as doing nothing, and find out whether
 the trained detector can be made to fire on the rendered scene at all. Both were
 settled by driving the running product in a browser and reading what came back,
 not by reasoning about the code.

 1. "RUN THE DETECTOR ON THIS CAPTURED FRAME" WAS RUNNING THE WHOLE TIME

    Measured: 520 ms on the first press, 298 ms on the second, real ONNX inference
    both times, on the same pixels. Nothing was broken. Three things hid it.

    THE ONLY VISIBLE TRACE WAS OFF THE SCREEN. The verdict paragraph sits below a
    full-width photograph. Measured in the running app at 1512x900: the button
    bottom is at y=621 and the verdict line at y=962. A control whose result you
    cannot see is a control that does nothing, as far as the person pressing it is
    concerned.

    THE ANSWER IS THE SAME ANSWER. Re-running on identical pixels returns an
    identical verdict, which is the property a measurement is supposed to have and
    is indistinguishable from a dead button.

    AND IT IS OVER IN 300 ms, so the "Running the detector..." label flashes past.

    The fix is a RUN LEDGER directly under the button, above the frame: one line
    per completed run, with its number, the wall clock, the inference time and the
    verdict. A repeat run adds a line, and a line appearing is visible whatever the
    answer says. When two consecutive runs are of the same pixels it says so, and
    says that the same answer is the point.

    No artificial delay was added. The reported millisecond figure is the measured
    one; making a 300 ms event look like a 900 ms one would be lying about the one
    number this panel exists to prove.

 2. THE VERIFY BUTTON WAS GENUINELY DEAD, AND THAT WAS THE BIGGER BUG

    Found while instrumenting the first one. "Verify - reproduce the committed
    0.91" runs this browser's pipeline over the committed evidence photograph and
    checks it against a figure written down before the code existed. It is the
    strongest claim in the product.

    The panel chose what to display with `byPanel[panelId] ?? last`. Once a drone
    had flown, `byPanel` held that array's filed capture forever, so the verify run
    happened and updated a value nothing on screen was reading. Pressing it after
    any flight changed nothing at all.

    A result now carries the array it is about, what it was run on, its run number
    and its clock time. The panel shows the most recent run ABOUT THIS ARRAY,
    captioned with what that was, and falls back to the flight capture. Only the
    flight files into `byPanel` - an operator re-running the detector can no longer
    destroy the frame the aircraft brought back, which was the failure the
    `?? last` ordering was originally written to prevent.

 3. THE MODULES ARE TEXTURED WITH PHOTOGRAPHS, AND IT TRANSFERS

    The detector was returning nothing on the render, which was the correct answer
    to the question it was being asked: it was trained on ground-level photographs
    and the scene was a flat-shaded blue rectangle with a polyline drawn on it.

    Two modules of the inspected array now carry actual photographs - the damaged
    one a cracked panel, its neighbour an intact one. This is a MATERIAL, not
    evidence, and it is what a digital twin is: geometry from the site plan,
    surface from photography. Both the cinematic and the incident file say so on
    screen, because at seven metres the render stops looking like a render and an
    audience would otherwise be entitled to read it as a camera frame.

    THE TEXTURES WERE CHOSEN BY MEASUREMENT, NOT BY EYE, and that mattered. Half
    the `Good`-labelled crops in the test split come back `Cracked` above 0.5 from
    our own weights - a real weakness of the model. Choosing the intact texture by
    looking at it would have manufactured a false positive on a healthy module.
    `scripts/make_panel_textures.mts` scores every written file and refuses to
    write an intact texture the detector calls cracked.

    NOT THE EVIDENCE FRAME. `IMG_0429` is the image the committed 0.9084 was
    measured on; texturing the scene with it and then scoring the scene would be
    teaching to the test. The generator refuses that file by name and a test
    asserts neither texture is it.

 4. THE ROI WAS THE REASON IT STILL DID NOT FIRE

    With the photographs on the modules the detector still returned nothing. The
    saved capture answered why. `LiveReticle` padded the module's projected rect by
    0.12 OF THE FRAME on each side, which more than doubled the crop: the model was
    handed three modules and a field of sand.

    Scored offline on that exact saved frame, with `scripts/score_image.mts`:

      whole frame (as shipped)   Saglam 0.942   no cracked box
      cropped to the module      Cracked 0.847
      tight on the module        Cracked 0.876

    So the fault was in the crop, not in the model. The margin is now a fraction of
    the module's own projected size rather than of the frame. Measured after the
    change, in the running app: `1 detection on that frame, at 0.63`, then 0.57 on
    a later capture. The detector fires on the render, and every box is still
    entirely its own output.

    Worth knowing: the model's top answer on the wide crop was `Saglam` - intact -
    at 0.94, which `crackedOnly()` discards before the UI sees it. The console then
    says "the model found nothing", which is true of cracked boxes and understates
    what the model actually said. Recorded in the backlog rather than changed here.

 5. WHAT WAS NOT MEASURED

    Inference times taken through headless Chrome on a software rasteriser ranged
    from 300 ms to 40 s depending on what the scene was doing. That is the software
    GL competing for the CPU, not the network. The figures the console prints are
    real; they need checking once on the machine that will run the demo.

 PHASE 23 - A REVIEW, A SWEEP, AND THE CHART THAT DESCRIBED ITSELF WRONG
================================================================================

 No bug report this time. The product was reviewed as code and swept as a running
 application, and the two found different things - which is the argument for doing
 both.

 1. A GATE FOR THE BUG THAT KEEPS SHIPPING - scripts/check_layout.mjs

    jsdom has no layout. Every element is 0x0, so a component whose content
    overflows its box renders identically to one that fits, and 508 unit tests
    stay green through it. This class of bug has now shipped twice: the module
    bodies in Phase 19, and the site KPI strip found here.

    THE KPI STRIP WAS 118px HOLDING 137px. `.area-kpi` does not clip, so the
    anomaly zone bars painted 19px down over the map on every screen in both
    themes - visible in every screenshot taken since the strip was built, and
    never noticed. The row is sized to its content now. Not clipped: clipping
    hides a reading instead of showing it.

    The gate walks six screens in both themes plus the array panel and the
    incident file, and reports any box smaller than its contents and anything
    painting outside the shell. Scroll regions are exempt - a scroll region is
    meant to be taller than its box - and a text node overflowing its own line
    box is typography, not a fault, so only containers are measured.

    FALSIFIED BEFORE IT WAS TRUSTED: with --kpi-h put back to 118px the gate
    reports the spill; at 140px it reports nothing.

 2. THE GENERATION CHART DREW NEITHER OF THE TWO THINGS ITS CAPTION DESCRIBED

    The caption promised a dashed line and a NOW marker. Querying the SVG: zero
    line curves, zero reference lines, and a legend reading "Delivered" twice.

    THE DASHED LINE WAS INSIDE AN <AreaChart>, WHICH RENDERS ONLY ITS AREAS. It
    was in the markup and in the React tree and drawn nowhere. ComposedChart now.

    AND IT WOULD HAVE BEEN INVISIBLE ANYWAY. `expected = delivered + shortfall`
    is 0.11 MW above delivered on a 400 MW axis - a tenth of a pixel. The caption
    described a gap nobody could see, which is worse than not drawing it. The
    same quantity is now plotted as the LOSS, in kW, on its own right-hand axis,
    where it is legible; the caption says so and says why it needs its own scale.

    THE NOW MARKER WAS DISCARDED BY A DUPLICATE CATEGORY. The x axis was
    categorical on clock labels and the curve spans a full day, so "10:00"
    appeared twice in the domain and the band scale could not resolve it. The axis
    is numeric hours with a formatter now, which is also what time actually is.

 3. ELEVEN REVIEW FINDINGS, NINE FIXED

    THE LIVE OVERLAY WOULD HAVE DRAWN THE COMMITTED PHOTOGRAPH'S BOX OVER THE
    SCENE. `LiveReticle` rendered whatever ran most recently. Press "reproduce the
    committed 0.91" while the aircraft is on station and that result - taken on a
    still photograph, carrying no ROI - would be drawn across the whole viewfinder
    as though the model had found a crack in the render. That is fabricated
    evidence, and it is the one thing the file exists not to do. It now draws only
    a run that came from this flight, over this array, with a crop.

    "RUN THE DETECTOR ON THIS LIVE FRAME" HANDED OVER THE WHOLE VIEWFINDER. The
    exact input this project has measured as returning Saglam 0.94 and no cracked
    box. Because the run carried the array's id it then replaced the pass's good
    capture with a whole-frame miss. Both callers share one `moduleRoi()` now.

    THE CLAMP WAS WRONG IN A WAY THAT MOVED BOXES. `x` was clamped to 0 and `w` to
    1 independently, so x + w could exceed 1: the model saw a narrower strip than
    the rectangle the overlay drew into, and every box landed stretched. The
    result now stores the region ACTUALLY cropped rather than the one requested.

    A FAILED RUN KILLED THE DETECTOR FOR THE SESSION. One bad frame set
    `status: 'failed'`, which `LiveReticle` treats as terminal, and nothing
    cleared it. "The model is unusable" and "this run failed" are separate states.

    `busy` WAS DOCUMENTED AS PREVENTING OVERLAPPING RUNS AND NEVER READ. Two runs
    both computed `runs + 1` after their awaits and took the same number - two
    ledger rows with one React key.

    THE MISSING-MODEL PATH KEPT NOTHING. Its comment said the captured frame stays
    on screen; the branch returned without storing it, so the whole "capture
    first, always" restructure had no effect in the one case it was written for.

    THE SURFACE-PROVENANCE NOTE WAS SCOPED TO THE SELECTED ARRAY, not the flown
    one - so an array no drone had been over was described as carrying
    photographed modules. Instance eleven of this project's most repeated bug,
    caught by review rather than by a screenshot for once.

    Also: an unread `press()` return in the new gate, so a renamed control would
    have made it measure the previous screen and still report success; a texture
    load with no error path under a caption asserting the photograph loaded; and
    two CanvasTextures leaked per retarget.

    NOT FIXED, RECORDED: a `shading` or `none` job books zero repair hours and
    still consumes a crew for travel, so a job with no work to do can push a real
    repair past its deadline - the one number DayPlan exists to report. Pre-
    existing, and moving it moves a headline figure; docs/backlog.md.

 4. DESLOP

    An unused `workOrders` parameter kept alive by a seven-line comment defending
    it - removed, with the caller. `Parameters<typeof reticleRect>[1]` where the
    type has a name. The `{ x, y, w, h }` shape written out three times, now
    `Roi`. A stale `label` field on the chart data. Two dead bindings the
    parameter removal left behind.

 PHASE 24 - FOUR PRESENTATION-LAYER BUGS, ALL MEASURED BEFORE AND AFTER
 31 Aug 2026
================================================================================

 Three reported by the owner on 30 Aug, one found while chasing them, all four
 recorded in docs/backlog.md 6e with their pre-fix measurements. Nothing here
 touches physics, data, the agent or the ranking.

 1. THE 3D CANVAS WAS SIZED TO `scale` OF ITS CONTAINER

    R3F measures its container with getBoundingClientRect(), which returns
    POST-transform pixels. The console is a fixed 1920x1080 shell that
    useFitToWindow CSS-scales into the window, so R3F sized the canvas to
    scale x 1920 and the wrapper then scaled it a SECOND time. The scene
    rendered into the top-left `scale` fraction and the rest of the frame was
    black.

    Measured before, during a real sortie at 1512x900:
      container   1920 x 1080 untransformed
      canvas      1512 x 850   - exactly the 0.7875 fit factor
      coverage    62% of the frame by area

    At 1920x1080 the scale is 1 and it is correct, which is why every
    screenshot harness in this project has missed it for four phases. On a
    1366x768 projector roughly half the cinematic would have been black.

    FIX: resize={{ offsetSize: true }} on the <Canvas>. react-use-measure then
    reads offsetWidth/offsetHeight, which ignore transforms.

    Measured after, same sortie: 100% coverage at 1512x900, 1920x1080 and
    2560x1450.

    AND A GATE FOR IT. check:layout now dispatches a drone and measures the
    canvas against its own container, failing below 98%. It reports the figure
    on every run whether it passes or not - a gate that cannot say what it
    measured is the failure mode this script's own header warns about. At the
    pre-fix geometry it scores 62% and fails.

 2. useFitToWindow CAPPED THE SCALE AT 1

    The cap was written to stop 52px type becoming 78px on a 4K monitor. That
    is right for a monitor and wrong for browser zoom, which is what people
    actually do: zooming out enlarges the CSS viewport and shrinks the device
    pixel ratio by the same factor, so a capped fit answers a zoom-out by
    drawing the console PHYSICALLY SMALLER inside a growing bezel. Measured
    before at 2560x1450: scale 1, a ~320px black bezel each side.

    FIX: the 1 came out of the Math.min. Measured after: 1.33333 at 2560x1450,
    exactly min(2560/1920, 1450/1080). The console is now zoom-invariant.

 3. THE RUN LEDGER CLAIMED "SAME PIXELS" ON DIFFERENT FRAMES

    The caption decided two runs shared pixels by comparing their SOURCE
    STRING. An inspection pass fires several runs under the identical string
    "the drone's camera over B-17" while the camera ORBITS, so the ledger
    printed "same pixels as the run above it - the same answer is the point"
    directly above 2 found / 1 found / 1 found / nothing found.

    The varying counts were correct and expected: legibility depends on the
    angle, which is why the pass keeps its best frame. The CAPTION was the
    defect. It was right in its other case - two Verify runs on the committed
    photograph - which is how it survived.

    FIX: RunLine carries a frameHash, FNV-1a over the encoded frame, and the
    caption compares that. Not the full data URL: holding four of those to
    answer a yes/no question costs megabytes.

    Measured after, in the browser:
      flight pass    1 found / nothing found / 2 found / 1 found - no caption
      two Verifies   1 found / 1 found on identical pixels      - caption shown
    Both branches now have unit tests; the second is new.

 4. FOUR EXPLANATORY NOTES LANDED IN ONE BAND

    Measured before at 1512x900, y positions 687 / 710 / 791 / 828: the
    detector's "the box is the module", the reticle's label tab, the
    surface-provenance line, and the flight-speed control. Each was added in a
    different phase to answer a different fair objection and none of them knew
    about the others. Individually defensible, collectively unreadable.

    FIX, by what each thing IS rather than where it sat:
      the two DISCLOSURES   merged into one ViewfinderNotes strip, bottom
                            centre, in the gap the PiP and the pill leave
      the reticle's tab     stayed - it is spatially bound to the module
      the speed control     moved above the status pill - it is a control

    ViewfinderNotes gates its detector line on the same predicate LiveReticle
    draws by, exported as useLiveBoxes(), so a caption cannot outlive the boxes
    it explains. SurfaceProvenance.tsx is gone; its content is the strip's
    first line.

    Measured after, in shell coordinates:
      notes strip    653..1267   (PiP ends at 627)
      speed control  1525..1888, y 961..996
      status pill    1668..1888, y 1001..1048
    Nothing overlaps anything.

 ALSO: THE EXPORTED DETECTOR IS NOW COMMITTED

    public/models/*.onnx was gitignored on the reasoning that this machine
    cannot generate the 11.7 MB binary and every clone would carry it. Still
    true, and now outweighed: the site is deployed, and a deployed build has no
    other source for the weights. Without them the console says "Detector not
    loaded" and the browser-side detection is absent from the thing people
    actually visit.

 PHASE 28 - THE ARRAY PANEL, AND AN AGENT THAT RECOVERS
 31 Aug 2026
================================================================================

 1. THE PANEL'S COLUMN LAYOUT HAD NEVER RUN

    Reported as "why not make it larger and divide it in 2 sides so we do not
    have to scroll". The wrapping-column layout was written when the wide card
    was built and it has never once applied: DetailPanel set `display: 'grid'`
    INLINE on the same element, and an inline style beats a class however
    specific the selector. globals.css even carries a comment saying exactly that
    about a different rule three lines below, which is how it survived.

    So every block rendered full width in one tall scrolling column, and the
    stylesheet described a layout nobody had ever seen.

    FIX: layout belongs to the stylesheet. The inline `display`, `gap` and
    `alignContent` are gone. The grid was documented as a fallback for "the
    demo's docked rail", which does not exist - ConsoleRoot sets `rail-over`
    unconditionally.

    Card 1180px -> 1520px, and the flex basis 320px -> 380px, which lands three
    blocks abreast at about 477px each. That is the width these blocks were
    originally drawn for as a 448px docked rail, so nothing is squeezed.

    Measured, B-17 at 1920x1080:
      before   one column, every block 1464px wide, scrollHeight over by ~1000px
      after    477px x 3, over by 187px - the approval gate is the only thing
               still below the fold, and it stays full width because the verdict
               and the gate must never share a line.

 2. THE PANEL ARRIVES INSTEAD OF APPEARING

    150ms rise-and-fade on open, and the vignette fades up with it rather than
    snapping on a frame earlier. The keyframe carries `translateX(-50%)` through
    every frame, because that is what centres the card - drop it and the panel
    flies in from the right edge. No spring, no overshoot; the reduced-motion
    rule zeroes it globally.

 3. A TRANSIENT AGENT FAILURE NOW HEALS ITSELF

    "AGENT UNAVAILABLE ... failing sometimes." A rate limit and a bad key were
    the same outcome to this store: `unavailable`, recorded against the array's
    condition, and then never asked again. Groq's free tier counts per minute and
    the site clock flips array statuses several times a second at 600x, so a
    burst of 429s was routine, and each one stuck until somebody found TRY AGAIN.

    FIX: an entry records `attemptedAt` and whether the failure is `retriable`. A
    429, a 5xx, a timeout or a dead socket are transient and the next `request`
    after six seconds asks again. A 400 or a 401 is not, and stays put rather
    than hammering a provider with a request that cannot succeed. The panel says
    "It will ask again shortly" when it will, because a panel that recovers
    silently reads as broken for the six seconds before it does.

    NOT A SECOND CLOCK. Nothing counts down. `request` compares two timestamps
    when it is called anyway - the same shape as the `condition` check beside it.
    CLAUDE.md rule 3 bans timers that DRIVE state.
